# EvoMu agent rules

## Goal and definition of done
- **Goal:** 100% feature parity with the live EVE Online server for the V24.01 client. This covers the classic machoNet surface, **all Quasar/public-gateway backend services**, and **ESI with SSO**.
- **Scope is the pinned parity ledger:** `.agents/skills/evomu-adversarial-review/references/parity/ledger.json`, plus the rows the gap auditor appends in `auditor_rows.json`. It has thousands of rows:
  - every client RPC method, notification, destiny action, Quasar proto, ESI operation and client static-data file;
  - all dogma effects;
  - curated game-mechanic rows (`feat:*`), plan tasks and real-client journeys.
- **Done means `/usr/bin/python3 .agents/skills/evomu-adversarial-review/scripts/final_gate.py` exits 0 on the current tree.** On that same tree it requires:
  - 100% of ledger rows closed;
  - a `PASS` claims review and a `CLEAN` gap audit;
  - workspace line coverage ≥ 90%;
  - mutation score ≥ 85%;
  - every real-client journey passing on the real V24 client, with clean logs.
- **The user reviews only for completeness, and only after the final gate passes.** Work as an unbounded loop:
  - Don't stop, ask for interim review, or ask the user to test.
  - Don't report the project as done or "playable" before the gate passes.
  - If you hit a true external blocker (credentials, hardware, a legal question), record it in `docs/BLOCKERS.md` and keep working on everything that isn't blocked.

- **Status tracking is generated, not hand-written.**
  - `docs/ACTION_PLAN_STATUS.md` is regenerated by `preflight.py` from the parity results, the plan and `git log`. **Never edit it by hand**; your edits are overwritten.
  - Record your own judgement per task in `docs/parity/task_notes.json`: `{"<task id>": {"assessment": "NOT STARTED|PARTIAL|DONE", "note": "<= 200 chars"}}`.

It is part of the gate: don't edit it. If you think an entry is wrong (the client really uses that proto), tell the supervisor with evidence. Quasar work should target the remaining open `quasar:*` rows, starting with the `eve_public` requests and notices the client actually sends or subscribes to.
- Put task IDs (e.g. `S-1`, `MN-04`, `Q-5`) in commit messages and in the claims file you give the reviewer.
- A task is `DONE` only when every "Done when" criterion is met by real, general logic (SDE-driven, no hardcoded IDs), and its tagged tests execute and pass.

## Independent review gate (mandatory)
- **When to run it.** Activate the `evomu-adversarial-review` skill (`.agents/skills/evomu-adversarial-review/SKILL.md`) and follow it before any of these:
  - claiming any work is complete, fixed, implemented, verified or passing;
  - `git commit` or `git push` (except local, never-pushed `wip/*` commits; see "Increment size and WIP");
  - editing status claims in `PLAN.md`, `README.md` or `docs/`;
  - ending a turn in which repo files changed.
- **The reviewer's verdict is authoritative.**
  - On **FAIL**, don't commit, push, or describe the work as done.
  - On **PASS_WITH_ISSUES**, **commit right away** and move on. Don't re-run reviews just to turn PASS_WITH_ISSUES into PASS. Fix the listed P1s in your next increment, or in the same one if you're touching that code anyway. They stay visible in `.evomu-reviews/latest.md` and `open_findings`. PASS is only required at the final gate.
  - Always record the verdict, the report path and whether tests actually executed.
- **Gap audits.** The orchestrator automatically chains a recall-focused **gap audit** every few reviews (or run `run_review.py --mode gap-audit`). Rows it appends are in scope immediately, and rows it flags as fake DONE count as open until a later audit clears them.
- **The Stop hook enforces two things:** an unreviewed tree must be reviewed, and a reviewed tree must keep making progress until `final_gate.py` passes.
- **Don't touch the gate.** Don't modify `.agents/`, `.evomu-reviews/` or the review hook, and don't disable the hook. Only the user may change the review gate.
- **Pre-push gate.** A git `pre-push` hook (shared by all worktrees) refuses to push `main` unless its code tree matches a tree that got a non-FAIL claims review in some EvoMu worktree (`.agents/`, `AGENTS.md` and local client-data symlinks excluded). Never bypass it (`--no-verify`, editing or deleting `.git/hooks/pre-push`, other remotes); that is gate tampering. If it refuses a push you believe is reviewed, tell the supervisor.
- **Keep local client data out of the tree.** `data/quasar_core_golden.json`, `data/quasar_descriptors.sqlite` and `data/evomu_sde.sqlite` are client-derived and must be gitignored, never committed.

## Honesty and verification
- "Verified" or "passing" requires real test execution output. `cargo check` and self-written scripts don't count.
- **Never type a number from memory.** Every count, size, row total, line reference or percentage in claims files, commit messages, `docs/`, `PLAN.md` or `README.md` must be copied from tool output you produced in the same session: the SDE manifest, `parity.md`/`parity.json`, `cargo test` output, `wc`, `ls -l`, `grep -n`. If you can't point to the output, leave the number out. Fabricated or stale numbers have caused most review FAILs so far.
- **Only claim a ledger row closed** when its tagged test exercises every clause of the row's `acceptance` text, through the RPC/notification names the V24 client actually uses (`references/parity/sources/`). Otherwise leave it open.
- **Data you derive or synthesize must be labelled as such**, never presented as imported (e.g. heuristic NPC spawn groups, formula-based rewards). Prefer importing the real data. If it doesn't exist in the client, record the gap in `docs/ACTION_PLAN_STATUS.md` and keep the row open.
- Unhandled RPCs must return `UnimplementedRPC`. Don't add constant, echo-only or wrong-semantics handlers to raise coverage numbers. Don't embed test fixtures in production code.
- Never bypass macOS Santa or other permission systems.
- evemu_Crucible is LGPL: re-implement its logic, never copy it.

## Pre-flight before every review (mandatory)
- Before `run_review.py`, run:
  `/usr/bin/python3 .agents/skills/evomu-adversarial-review/scripts/preflight.py --claims /tmp/evomu_claims.md`
  It takes about a minute, against about ten for a review.
  - It runs the tests and the parity check.
  - It prints authoritative numbers and a claims template (`.evomu-reviews/preflight/claims_template.md`).
  - It lints your claims for untraceable numbers, bad `path:line` references, quotes that don't exist in the repo, and ledger rows that aren't closed.
- **Copy numbers from the template; don't type them.**
- **RPC-name check (blocking).** Pre-flight checks every RPC service/method and `On…` notification name on lines you added or changed since the last review against the identifiers in the real V24 client code (`code.ccp`, parsed locally and cached in `.evomu-reviews/`).
  - A name the client code doesn't contain can't be a client RPC. Use the client's real method name instead of an invented or Crucible-era one: e.g. no `marketProxy.PlaceCharOrder`, `dogmaIM.FireWeapon`, `invbroker.MoveItem`, `planetMgr.CreateColony`, `wormholeMgr.JumpWormhole`.
  - The only escape is `rpc-lint: allow <reason>` on that line or the line above. The reviewer checks every such reason.
  - Repo-wide there are about 610 legacy violations (see `metrics_rpc_names.txt` in each review's context). Rows whose tests depend on them are suspect; remove or replace them as you touch those areas.
- **Don't start a review until pre-flight prints `OK`.** Every lint problem must be fixed or explicitly explained in the claims. For example, a row you mention as still open, or a number about removed code that you cite with its commit hash.
- **Early Sanity Gate (< 2 seconds).** Pre-flight runs static checks *before* `cargo test` (RPC names, hollow assertion anti-patterns like `check_handled`, permissive status codes, fake Quasar descriptor sweeps, and claims citations). It aborts immediately on P0 violations. To override and run the full test suite anyway, pass `--skip-early-fail` (or `EVOMU_PREFLIGHT_SKIP_EARLY_FAIL=1`). Run `preflight.py --early-only` to test diff sanity in 1 second without running tests.
  - **Tagged tests** touched by the diff are blocked if they tag more than 15 non-data rows (`TOO_MANY_ROWS_PER_TEST`), have no value assertions — only `matches!`/`is_ok`/`status_code`/non-empty checks (`SHAPE_ONLY_TEST`) — or have fewer than one value assertion per 3 tagged rows (`THIN_ASSERTIONS`). `sde:`/`effect:` rows are exempt (data sweeps). Escape: `// parity-lint: allow <reason>` in the test's comment block; the reviewer checks every reason.
  - **Constant RPC handlers** (`CONSTANT_RPC_HANDLER`): more than 5 newly added handler arms that return a constant (`None`, `Bool`, empty list/dict/tuple) without reading or writing state block the run. Implement the semantics, return `UnimplementedRPC`, or justify a genuinely constant answer with `// const-ok: <reason>` on the arm. The full list is written to `.evomu-reviews/preflight/early_gate.txt`.
  - **One integration-test binary** (`NEW_STANDALONE_TEST_BINARY`): once `crates/eve-server/tests/it/main.rs` exists, new files directly under `crates/eve-server/tests/` are blocked; put them in `tests/it/` and add a `mod` line. When you port work from older branches, move their test files into `tests/it/` too.
- **Test-loop timing is recorded automatically.** Every pre-flight appends wall, build and test-run times to `<main checkout>/.evomu-reviews/preflight_history.jsonl` and prints a "Test loop" line in the claims template. Don't edit that file; the supervisor tracks the trend.
- Pre-flight also lists the rows newly closed since the last review, with their acceptance text. Re-check that every clause is really tested before claiming them.

## Code layout: split the monoliths (one-time, right after Phase 1 commits)
- The biggest drag on your throughput is re-reading a few huge files in 800-line windows: `crates/eve-server/tests/e2e_journeys.rs`, `crates/eve-db/src/lib.rs`, `crates/eve-server/src/router.rs`.
- In a **separate, behaviour-neutral change** (task tag `S-REFACTOR`, no ledger rows):
  - split tests into per-area files under `crates/eve-server/tests/` (`auth.rs`, `character.rs`, `inventory_fitting.rs`, `space.rs`, `combat.rs`, `market.rs`, `industry.rs`, `missions.rs`, `social.rs`, `structures.rs`, …) with shared helpers in `tests/common/mod.rs`;
  - split `eve-db/src/lib.rs` into domain modules (`accounts`, `characters`, `inventory`, `market`, `industry`, `missions`, `corp`, `persistence`, …);
  - split `router.rs` into dispatch, binding/monikers, and session handling.
- Keep every test function name and every `// parity:` tag unchanged. Aim for files under about 1,500 lines.
- Claims for that review: the passed-test count and the parity numbers are identical before and after (paste both pre-flight outputs), and the change has no behaviour edits.
- From then on, keep new code in this layout.

## Parallel delegation (subagents)
- **Never let two agents edit the same working tree.** Any edit while a review runs makes that review INVALID, and concurrent edits clobber each other. Every subagent that writes code gets an **isolated workspace**: a `branch`/`share` workspace, or a `git worktree add ../EvoMu-<track> -b track/<track>`. Read-only research subagents may share the main tree.
- **In effect now.** Phase 1 and `S-REFACTOR` are committed, so the orchestrator must keep **at least 3 independent tracks running concurrently**, each a subagent in its own worktree, while it merges and reviews. Working serially on one track is a process violation unless every remaining open task depends on that one track.
- **Tracks that can run in parallel once the refactor lands** (one subagent each; the orchestrator keeps the canonical status file):
  - T-1/T-3/T-5 (test kit, proptest/fuzz, coverage and mutants);
  - T-2 (SDE sweeps);
  - P-1…P-5 (wire codec, object cache, config service, notifications);
  - P-6/ESI-1 (native handshake plus SSO/launcher tokens);
  - P-7/SP-1/SP-2 (binary destiny, celestials, bubbles);
  - Q-1/Q-2 (protobuf extraction plus gateway);
  - ESI-2 (HTTP framework).
  - Later phases split by domain (mining, market, industry, PI, corp, sov/FW, structures, each Quasar family, each ESI tag group), following the plan's dependencies.
- **Every track follows the same gate in its own worktree:** pre-flight, `run_review.py`, and a non-FAIL verdict, before its branch is merged.
  - Each worktree has its own `.evomu-reviews/` state, Stop hook and review history.
  - Share the static data with `EVOMU_SDE_PATH=/Users/sergeya/ai/EvoMu/data/evomu_sde.sqlite`.
- **Merging into `main`** is done by the orchestrator, one track at a time: rebase or merge the reviewed branch, run pre-flight on `main`, then run a claims review of the merged tree. Never push or merge an unreviewed tree.
  - **Exception — identical code:** if the merged tree differs from a tree that already got a non-FAIL claims review (in any EvoMu worktree) only in supervisor-owned gate files (`.agents/`, `AGENTS.md`), and those match `main`, no new review is needed. The gate checks this mechanically (`review_lib.reviewed_by_code`; the Stop hook and `final_gate.py` accept it). Put the reused review's timestamp in the merge/push message. Pre-flight on `main` is still required.
- **Subagents must get `AGENTS.md` and the plan as context** and obey every rule here. No subagent may modify `.agents/`, disable hooks or bypass Santa. Delegation doesn't relax any rule.
- **Subagent reports to you are claims, not facts.** Verify them with pre-flight and the review before recording anything in `docs/ACTION_PLAN_STATUS.md`.

## Reviewer unavailable (quota or capacity outages)
- **How the orchestrator handles quota errors.** `run_review.py` tries the primary reviewer (`opus-5.5-high`, Claude Opus 5.5 High) first, then the fallbacks `auto` (Gemini Pro Next), `gemini-launch-candidate-high`, `gemini-flash-next` and `fable-5.1-high` (`EVOMU_REVIEW_FALLBACK_MODELS`).
  - A fallback verdict is a real review and gates commits normally. The report says which model reviewed.
  - The final gate still needs a PASS from the primary model.
- **If every model is out, the review returns `UNAVAILABLE` (exit code 4).** Nothing was reviewed, so never treat it as a pass. Also don't treat a user instruction to "keep developing while the reviewer is down" as permission to skip the gate. While the reviewer is unavailable:
  1. **Never commit, merge, cherry-pick or push to `main` or to any `track/*` branch.** Commit only to local `wip/<task-id>` branches, one task per branch, never pushed. Subagents follow the same rule in their worktrees.
  2. **The free gates still apply to every wip commit:**
     - `cargo test --workspace` passes;
     - `preflight.py --claims` prints OK;
     - `cargo mutants --in-diff` on the change;
     - no RPC or notification names that aren't in the V24 client catalog (`references/parity/sources/`);
     - no hardcoded or synthesized data presented as real.
  3. **Prefer work that's hard to fake and easy to check mechanically:** SDE importers and data sweeps, test and harness infrastructure, property and fuzz tests, wire codecs with golden tests, behaviour-neutral refactors. **Don't start new game-behaviour features** (mechanics, RPC handlers, Quasar/ESI services). Invention hides there, and it compounds without review.
  4. **Keep each wip branch to one canonical task and a reviewable diff size.** Don't stack later work on unreviewed earlier work unless it truly depends on it.
  5. **Keep a queue** in `docs/parity/review_queue.md`: one line per wip branch with task ID, branch, pre-flight result and date. When quota returns, review the queue **in order, one branch per review**, and merge each into `main` only after its own non-FAIL verdict. Rebase later branches as needed.
  6. **Re-try the review** at most once an hour while unavailable. Don't burn time polling.
- **This rule exists because of a real failure.** During the 2026-10-18 outage, about 80 unreviewed commits were merged and pushed to `main`. They included about 6,000 lines of invented Quasar services and tests against RPCs the client never calls, and 72 ledger rows were later flagged fake. Cleaning it up took longer than reviewing per task would have.

## Increment size and WIP
- **Review one canonical task (or a few tightly coupled ones) at a time**, not a whole phase. Smaller diffs review faster and fail more narrowly.
- **To avoid losing work while a review is failing**, you may commit to a local `wip/<task-id>` branch without a review.
  - Never push `wip/*` branches.
  - Never merge or cherry-pick into `main` without a non-FAIL review of the exact tree.
  - `main` stays review-gated.

## Client-derived data and the public repository
- `origin` (`github.com/saverchenkov/EvoMu`) is **public**. Never commit or push data extracted from the EVE client:
  - no `.fsdbinary`/`.static` content;
  - no SQLite databases or JSON dumps built from them, including "fixtures" or subsets. An import manifest of only table row counts and file checksums is fine;
  - no client code, bundles or dylibs.
- The full SDE database (`data/evomu_sde.sqlite`) stays local and gitignored, built by `tools/sde-import` from the operator's own client install. Tests that need real static data open it through `EVOMU_SDE_PATH` or the default path, and **fail loudly** when it's missing. They never skip silently and never fall back to client-derived subsets.
- A tracked CI fixture is allowed only if it's **synthetic**: generated by a script from invented values that follow the schema, and clearly named as synthetic. Tests that close ledger rows must run against the real local SDE, not the synthetic fixture.
- Remove any `.gitignore` exception that would track client-derived data (e.g. `!/data/evomu_sde_fixture.sqlite`), unless that file has been replaced by a synthetic one.
